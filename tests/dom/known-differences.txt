# Facts where this port deliberately does not match the browser, and why.
# Format: probe file | fact name | reason
#
# Anything not listed here must match. A difference that is really a bug
# does not belong in this file.

forms.html | input value write | A control's value property is its current value and the value attribute is the default it resets to. Here the renderer draws the control from the attribute, so writing the property has to write the attribute or the user never sees what a script typed into the field. defaultValue and reset still return the original, which is remembered the first time the value is overwritten.

collections.html | characterSet | A document that declares no encoding is decoded as UTF-8 here and as windows-1252 by the browser, which falls back by locale. That is the parser's default, not a binding: characterSet now reports whatever NetSurf actually decoded with, which is the honest answer either way.

text.html | comment data | innerHTML that is nothing but a comment parses to no child here. A comment anywhere else in the markup comes through as a comment node, and document.createComment makes a real one, so this is hubbub's handling of a fragment whose entire content is a comment, not the bindings.

One prototype for every node
  Every node here shares Node.prototype: there is no separate
  HTMLDivElement.prototype, Text.prototype or XMLDocument.prototype for
  a prototype chain to walk. instanceof and constructor answer the right
  interface, but a test that compares Object.getPrototypeOf(node) with a
  named interface's prototype cannot pass, and one that walks the chain
  Text -> CharacterData -> Node finds one link where a browser finds
  three. That is the shape of these bindings, not an oversight: a single
  prototype is what lets a page patch one place and have every node see
  it, which is what the polyfills on real pages do.
  Affects, among others: DOMImplementation-createDocument (most of it
  is gated on XMLDocument.prototype), Text-constructor and
  Comment-constructor ("prototype chain").

SVG element names are upper-cased
  libdom stores every element name upper-cased, so an SVG clipPath is
  held as CLIPPATH and the capital P cannot be recovered. localName
  lower-cases what libdom gives, which is right for HTML and no worse
  than before for SVG. Fixing it means patching libdom's element
  creation, which NetSurf's own code compares against.
